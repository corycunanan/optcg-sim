# Replacement scan continuation contract (OPT-968)

The reader prerequisite supports native game-state version 6 while ordinary producers remain version 4 (or existing trigger-generation version 5). The writer follow-up enables version 6 and removes the temporary legacy replacement module in this same rollout. Versions 1–5 and their converters remain supported. A deployed semantic version-6 reader is the rollback floor after writer deployment; dc08a5ac cannot read new replacement progress. Synthetic engine-produced fixtures do not replace captured production sessions; the coordinator must disposition the outstanding capture gate before deployment.

## Ownership

Publication remains with action events and the common pending-work drain. Replacement scanning orders and rechecks candidates; it does not publish or advance the scheduler. The existing REPLACEMENT and REPLACEMENT_BATCH frames own waiting progress. Prompt lifecycle consumes answers, the batch continuation reports original consequences, and BATTLE_DAMAGE finishes its original K.O. and battle once. Accepted hand-trash, destination-choice and owner-arrangement substitutes retain their normal resolver frames above the parked caller. Terminal processing and frame cleanup retain their existing owners.

## Version 6 fields and inference

REPLACEMENT adds optional `visitedEffectIds`, `cause`, `causingController`, and `orderingEffectIds`. REPLACEMENT_BATCH adds optional `visitedEffectIds`, `events`, `cause`, and `orderingEffectIds`. `pendingMatches/currentMatchIndex` identify the current offer or accepted substitute; the visited set identifies declined or completed effects. A current ordering decision is a PLAYER_CHOICE, followed separately by an OPTIONAL_EFFECT when the chosen replacement is optional. Version-6 progress under an older schema version is rejected. New arrays are strict, and ordering references must agree with the candidate set and prompt.

Loaded version 6 retains `GameState.schemaVersion = 6` through copying, later pauses, completion and persistence, including supported undo state. It cannot silently downgrade after its replacement frames disappear. A historical single offer has no completed candidates; its cause/controller are inferred from the parked battle or caller. A historical batch infers completed candidates from its recorded prefix before `currentMatchIndex`, preserving the original current offer. No fields are hidden in result references. The existing `REPLACED_CARD` reference remains the semantic identity used by substitutes and selects their strict choice-branch feasibility gate.

## Rules policy and execution

The affected event card's own replacement precedes the turn player's chosen ordering, followed by the non-turn player's chosen ordering. This is Decision 7's **assumed literal reading, with no official ruling**; it is isolated in `replacementPrecedence` and its fixture. Current official rules 1.2.1 replacement clauses agree with the repository's 1.2.0 text; this change does not migrate the global rules version.

Battle and batch use the same candidate scanner before offers and commit. Declines and completed applications are not offered again for that original situation. Each completed substitute rescans still-unprotected targets, including previously ineligible candidates. No original member leaves before the batch has finished its applicable replacements, so one payment covers the matching batch and a removed sibling cannot fund another member's payment.

Hypothetical checks execute real action handlers on private state, retain sequential state/results, validate real selections and full target counts, and discard prompts/events/IDs/RNG changes. Resource handlers report whether the full instruction executed while ordinary effects may still resolve partially. Choice branches are checked when reached and again when selected. Existence selections are lazy, including Koby's required-three trash payment. Destination and owner-arrangement checks use actual handler execution; committed execution retains the player's prompts.

The attached-DON return domain deliberately retains its existing printed-field feasibility gate and amount-only underpayment allowance pending OPT-969. The real executor still returns available cost-area DON!! before later instructions are probed; sequential return-then-rest cannot reuse returned resources. All five current RETURN_DON_TO_DECK consumers have no following substitute action. This retained domain exception does not claim attached-DON payment correctness; this work does not repair or search activation-cost replacements. The probe refuses unsupported prompting operations rather than treating every prompt as feasible. Inventory on this revision covers all 15 currently authored nested replacement action types; source/generated parity is separately checked.
