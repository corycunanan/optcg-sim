## Advancement contract and ownership

`HandlerResult` carries `completed`, `waiting`, `queued`, `continued`, or `terminal`. The facade's exhaustive `advanceHandler` switch consumes these tags: waiting returns without advancing; completed advances only an existing owner; queued/continued enter the executor; terminal enters its terminal-first cleanup. Rejected replies restore the original state unless the handler deliberately refreshed its prompt. Tags are returned at domain exits, rather than reconstructed after a private cross-effect drain.

| Family | Local responsibility and exit | Central consumer |
| --- | --- | --- |
| Cost (`handleAwaitingCostSelection`, `finishCostsAndRunActions`, `abortReplacedCost`) | Validate/pay/abandon costs; execute the same effect's suffix; waiting for another payment, terminal on termination, otherwise report fresh triggers as queued/continued | `advanceHandler` → `advanceTriggerExecution` |
| Choice / optional / state distribution / field-to-Life | Validate response and preserve same-effect suffix; reject/wait, explicit terminal, or report queued work | Same facade; ordering choice selects the stored generation before advancement |
| Target / overflow / DON redistribution | Preserve selection, payment, result references, replacement and play boundaries; branch helpers return local continued or a terminal HandlerResult | Core dispatcher finishes local action chain, then facade consumes its result |
| Deck arrangements / search / Life reorder / scry | Local state transformations and validation; these helpers never own cross-effect scheduling | Core `resumeEffectChain` emits waiting/terminal/completed or reports fresh matches |
| Interrupted / simultaneous continuation | Resume the exact saved suffix or action plan; retain committed prefix at a legal owner | Core dispatcher, then shared executor |
| Batch reentry | One batch step and its same-effect suffix, explicit terminal before/after work; reports fresh work without privately draining | Only `advanceTriggerExecution` calls `reenterBatchResume` |
| Direct effects / scheduled effects | Establish an empty ordinary owner beneath their own continuations before execution; condition-false/rejected activation restores original identity allocation | Shared executor after local result; scheduled phase iteration remains domain-owned |
| Life Trigger / battle / effect damage | Existing damage frame retains ordinary debt; accepted Life Trigger's own children finish before its exact damage boundary | `advanceLifeTriggerExecution` invokes the same executor with exact stop frame; ordinary generations remain deferred |
| Replacement | Preserve replacement batch, original suffix, and publication debt; no private trigger scheduler | Existing session continuation dispatch returns to the common resolver/executor |
| End Phase / turn handoff | Existing phase driver owns ending-player wave, opponent wave, scheduled effects and handoff | Each effect/window uses the shared owner; no PR9 outer-drain consolidation |

## Ordering and publication

Ordinary older generations finish before fresh triggers. An explicit collector joins reports from one effect and from older siblings until the entire older generation finishes. **Grouping C and D raised by older siblings A and B into a subsequent choice is the user's approved interpretation**, not a direct claim that an FAQ explicitly addresses this exact synthetic scenario. Existing closed generations and ordering history remain separate. Same-controller ordering IDs are unique within a collector; recurrence across different closed generations is valid.

Rules v1.2.0 8-6-1 / 8-6-1-1 and OP10-042's non-turn-player FAQ motivate A→X→C and A→B→C. Rule 8-6-3 requires the current effect's suffix before new ordinary effects. Rule 8-6-2 defers ordinary damage triggers; 8-6-2-1 permits the Life Trigger itself between damage points. Attacker damage windows remain explicit windows. End Phase ending-player waves finish before the opponent wave.

OPT-975 old duplicate sites were independently tagged at baseline `f3924a47`: `resume/triggers.ts:71` published CARD_PLAYED, `resume/triggers.ts:178` published POWER_MODIFIED, and `trigger-queue.ts:178` published both returned events again. The new common publication boundary respects the event's independent `eventLogEmitted` and `triggerScanned` obligations. Distinct equal-payload events are not deduplicated by payload. Committed parent prefixes are transferred to the nearest eligible ordinary owner or matching live battle debt; future Event completion notifications stay on completion-only boundaries.
