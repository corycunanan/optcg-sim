## Failure classes to prove or rule out
1. **Printed order + all-or-nothing (8-3-1-1, 8-3-1-3).** OP13-007: give DON first, then trash self. If TRASH_SELF then fails (e.g. a prohibition), the given DON!! must be rolled back (cost transaction). Declined or unpayable → no post-colon action, no DON moved.
2. **Only ACTIVE, unattached DON!! in the cost area count.** Rested DON!! and DON!! attached to cards do not. What state does a given DON!! end in (the action's existing semantics / rules for "give")? Cite the rule.
3. **Recipient filter.** OP13-007: any of your Leader or Characters (can it be OP13-007 itself, which is then trashed? Derive from text/rules; if legal, the DON!! returns per the zone-transition contract — test it). Rayleigh cards: Leader or Character named Silvers Rayleigh only; no recipient → unavailable.
4. **Events exactly once.** DON-given watchers/conditions (e.g. `DON_GIVEN`, "when DON!! is given" triggers, OP12-016's "the card given these DON!! cards") must observe the cost payment exactly once and identically to the action. Inventory consumers via the registry. OP12-016's post-colon clause references the recipient — make sure the recipient chosen during cost payment is available to the effect (cost result/ref) and the attack-scope prohibition binds to it; if that binding needs vocabulary that belongs to OPT-826 (attack scope bound to selected card), implement only what the cost must expose and report the rest as a Follow-up rather than building OPT-826.
5. **Persisted prompt / resume.** Recipient (and DON if chosen) selection serializes and resumes exactly once; stale/duplicate responses cannot double-pay.
6. **No regression for other DON costs** (`RETURN_ATTACHED_DON_TO_COST`, `GIVE_OPPONENT_DON`, `REST_DON`, `DON_MINUS`) — inventory their consumers; do not change `GIVE_OPPONENT_DON` semantics (OPT-868 owns that), just stop OP12 using it.
